> 2026-11-23。一次完整的从零搭建，记录了当时为什么这么选、实测到什么、踩了哪些坑。
> 代码在同一个仓库；原理与调参说明见 `README.md`。

## 起点：一个预设错误的问题

最初的问题是：「如果我想用服务器来做一个 AI，该干些什么」。

聊下来发现这个问题本身预设错了——它把「做 AI」当成一件需要先有机器才能开始的事。实际上是反过来的：**先说清楚要做什么，才知道需要什么机器**，而且很多时候根本不需要服务器。

---

## 一、先分档，再谈硬件

| 档位 | 做什么 | 显存需求 | 上手周期 |
|---|---|---|---|
| 部署现成模型 | 跑开源权重，做问答、知识库、智能体 | 8–24 GB | 1 周 |
| 微调自己的模型 | 用自己的数据训练，让它学会特定任务 | 24–48 GB | 1 个月 |
| 从零预训练 | 训基础大模型 | 640 GB × N 卡 | 不现实 |

结论：**90% 的「做 AI」停在第一档，而第一档通常不需要一台独立服务器**——一台显存 8G 以上的笔记本，或者按量租的云实例就够。

---

## 二、租还是买

| | 租云 GPU（按量） | 自己买机器 |
|---|---|---|
| 起步花费 | 几块到几十块 | 1.5–3 万（4090 整机） |
| 适合 | 验证想法、间歇训练 | 每天跑、长期跑 |
| 隐性代价 | 忘关机等于烧钱，数据要上传 | 电费、噪音、占地、折旧 |

判断线：**先租，跑满 150–200 小时、花掉三五百块之后，再决定买不买。**

## 三、AI 助手其实是三层

```
应用层    上下文拼接 · 记忆 · 知识库 · 工具调用 · 界面      ← 90% 工作量，也是唯一「你的」
推理引擎  Ollama · llama.cpp · vLLM · transformers         ← 装个工具
模型权重  Qwen · DeepSeek · Llama                          ← 别人花千万训的
```

「从零」有三种深度，价值完全不同：

1. **应用层从零（选了这条）**：模型当黑盒，自己写上下文、记忆、检索、界面。几小时到几天出可用产品。
2. **推理层从零**：用 transformers 手写 generate 循环、KV cache、采样。一周，能彻底理解「一个 token 一个 token 往外吐」，但性能比 Ollama 差十倍。
3. **模型层从零**：tokenizer → Transformer → 预训练 → SFT → 对齐。几个月集群 + 千万预算，训出来大概率不如现成的 3B。

## 四、实际搭建

### 环境

| | |
|---|---|
| CPU | i5-12500H（12 核 16 线程） |
| 内存 | 15.6 GB |
| 显卡 | RTX 3050 Ti Laptop，**4 GB 显存** |
| 系统 | Windows，Python 3.13.14 |
| 磁盘余量 | 233 GB |

4GB 显存是硬约束，所有选型都围绕它。

### 选型与理由

| 组件 | 选择 | 为什么 |
|---|---|---|
| 推理引擎 | Ollama 便携版（解压到 `C:\Users\ASUS\ollama-portable`） | 不用管理员权限、不写注册表、不装服务，删目录即卸载 |
| 对话模型 | `qwen2.5:3b`（1.9G） | 非推理模型，直答；实测首字 0.59s |
| 备选模型 | `qwen3:4b`（2.5G） | 逻辑题更强，但思考太长，见下文 |
| 向量模型 | `nomic-embed-text`（274M） | 够小，能和对话模型共存于 4G 显存 |
| 后端 | FastAPI，全部手写 | 不引 LangChain 之类框架，每一行都能读懂 |
| 前端 | 单文件 HTML + 原生 JS | 无构建、无 npm、无 CDN 依赖 |
| 存储 | SQLite 三张表 | `sessions` / `messages` / `kb`，随时可查可删 |
| 检索 | Ollama `/api/embed` + 纯 Python 余弦 | 不引 numpy，几百个块用不着 |

### 一次对话的数据流（`server.py` 的 `chat()`，40 行）

```
你打字
  → 向量化问题，和 kb 表里所有块算余弦，取最像的 4 块
  → 拼 messages：[system 人格] [system 检索资料] [历史×24] [本次问题]
  → POST 给 Ollama，token 一个个吐回来
  → 每块 SSE 推给浏览器，界面实时追加
  → 完整回答存进 messages 表
```

所有「AI 助手」的差别——记不记得住上下文、会不会引用资料、回答风格——全在这 40 行，不在模型里。

## 五、两个值得记下来的坑

### 1. Qwen3 的思考停不下来（选型翻车现场）

第一版默认用 Qwen3-4B，因为它更新更强。实测：

> 问「光速是多少」，答案只有 18 个字，模型内部却生成了 **1184 个 token、跑了 51 秒**。

Qwen3 全系是「混合思考」模型，回答前在内部生成一大段推理。试了两种关法，都不解决问题：

- 请求参数 `think: false` —— 在 Ollama 0.40.17 上无效
- 官方软开关 `/no_think`（加在 user 或 system 末尾）—— **思考过程不再显示，但 token 一个没少**

换 `qwen2.5:3b` 后，同一问题 1.8 秒答完。

**教训：本地部署不是模型越新越好。要看它的推理模式跟你的显存匹不匹配——在算力紧的机器上，「会思考」是负资产。**

### 2. Ollama 在 Windows 上分片下载卡在最后一步

现象：`ollama pull` 下到 100%，blob 文件大小已经等于清单里的总大小，但文件名一直是 `sha256-xxx-partial`，`ollama list` 里看不到模型。CPU 也不动了。

原因：分 16 个 ~156MB 的片段下载，最后合并阶段卡住。

解决：**杀掉 pull 进程，重新执行一次 `ollama pull`**。已经下好的数据会被复用，几秒钟就 `writing manifest` + `success`。

这个坑在 qwen3:4b、nomic-embed-text、qwen2.5:3b 上各遇到一次，是稳定复现的行为，不是偶发网络问题。

### 3. 两个小 bug

- `init_db()` 定义了却忘记调用，启动后第一个请求就 `no such table: sessions`
- 模型没预热时首次对话要等 30 秒（冷加载）。改成启动时用后台线程各发一次空请求，把对话模型和向量模型都推进显存

## 七、被否掉的方案

记下来，免得以后又走一遍：

| 方案 | 否掉的原因 |
|---|---|
| 先买一张显卡自建服务器 | 使用频率未知，买错卡的概率高；先按量租更理性 |
| 从零预训练模型 | 预算与算力差三个数量级，且效果不如现成 3B |
| 默认 qwen3:4b | 实测 51 秒答一句，体验不可接受 |
| Open WebUI / LangChain 等现成框架 | 功能过剩、依赖重、出问题难定位；手写 380 行反而清楚 |
| 用 numpy 做向量检索 | 几百个块的余弦距离，纯 Python 完全够，少一个依赖 |
